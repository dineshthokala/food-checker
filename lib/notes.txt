Screen flow

Splash → Login/Register → multi-step Onboarding → Home (food search) → Result → Report / "Still want to eat?" buttons.

Break onboarding into 3 to 4 short steps with a progress bar (conditions, body measurements, personal details), and save each step as you go so nobody loses progress. Since this is a health app, I'd also add allergies and current medications (or at least "blood thinners" and "diabetes medication"). These change food advice more than most other fields.

Data model (Supabase)
profiles: user id, age, gender, height, weight, ethnicity, blood group
user_conditions: user id, condition
food_decisions: user id, food, conditions snapshot, decision (will_eat / wont_eat), timestamp
food_reports: user id, food, report type (false positive, false negative, incorrect info, other), comment, and a full snapshot of what the app showed (profile snapshot, verdict, text, model version, sources)
food_cache: normalized food + profile bucket → verdict and text

Enable row-level security so users only see their own rows. Store the snapshot in reports, because you can't investigate a complaint without knowing exactly what was shown.

Report notifications: a Supabase database trigger or webhook on food_reports calls an Edge Function that posts to Slack, Telegram, or email. That's about an hour of work and needs no app changes.

Getting accurate food information (your point #8)

From easiest to most accurate:

Level	Approach	Accuracy	Notes
1	LLM alone with structured JSON output	Low to medium	Fast to build, but can hallucinate confidently
2	LLM + live web search	Medium	Adds freshness and citations, but web quality varies
3	LLM + retrieval over trusted sources (USDA FoodData Central, IFCT, ADA/DASH/KDIGO/ICMR-NIN guidelines)	Medium to high	Answers grounded in vetted text
4	Nutrient database + rule engine, with the LLM only phrasing the short sentences	High, auditable	Same food gives the same verdict every time
5	Level 4 with rules reviewed by a dietitian, plus verified verdicts cached	Highest	What you promote answers to over time

Web scraping is the weakest option. It's brittle, often against site terms, and quality is inconsistent. Prefer APIs and open datasets.

My recommendation is a hybrid. Launch with Level 3 (retrieval-grounded LLM) so you have coverage on day one, cache every answer, and use your report button and a dietitian to steadily promote frequent foods to Level 4/5. Two hard rules apply:

LLM calls go through a Supabase Edge Function, never directly from the app, so the API key can't be extracted.
The model returns structured JSON (verdict, 2 to 3 short sentences, portion tip, alternatives), so the UI is consistent and you can validate the output before showing it.
Two things I'd push back on
Blood group: collect it if you want it for the profile, but I wouldn't let it influence verdicts. The "blood type diet" idea has weak scientific support, and using it could make advice less accurate.
Ethnicity: this is genuinely useful. For example, risk thresholds for diabetes and BMI differ for South Asian populations, and it helps with regional food coverage.
Compliance and store review
Use cautious wording in results ("generally advised to limit") plus a visible "not medical advice" note.
Health apps get closer scrutiny at App Store review, and Apple requires in-app account deletion whenever you offer account creation. Build that in early.
You're storing health data linked to identity. Get explicit consent at onboarding and write a privacy policy that covers it.
Performance and UX
Debounced search with local autocomplete from a foods table, so most searches don't need an AI call
Cache hits return instantly, and a skeleton loader covers the rest
Keep answers to 2 to 3 sentences, with the verdict badge (Good / Limit / Avoid) shown first
Cache recent searches for offline viewing
Keep the "yes" confirmation non-judgmental (a portion tip works better than a scolding), and make the "no" celebration short and warm
Suggested build order
Project setup: architecture, theme, routing, Supabase connection
Auth and onboarding screens with saved progress
Home search, result screen, and the Edge Function (starting with Level 3)
Decision buttons and logging, then report button and notifications
Dietitian review of rules, then testing
